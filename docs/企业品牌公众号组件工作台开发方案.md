# 企业品牌公众号组件工作台开发方案（V2）

## 一、项目定位

本项目用于根据企业品牌资料，生成一套专属的微信公众号文章组件。

用户提供企业品牌信息后，系统完成：

- 分析企业品牌视觉语言
- 生成品牌资源和品牌规范
- 一次性生成整套品牌组件初稿
- 在工作台中逐个预览和审核
- 对不满意的组件单独提出修改
- 保留组件版本并确认最终版本
- 将品牌组件应用到已有公众号文章
- 输出符合程序规范和公众号兼容要求的 HTML

> 项目的核心不是生成一篇文章，而是**生成并维护一套可长期复用的企业品牌组件库**。

### 设计哲学

> **AI 不直接创造最终结果，它参与品牌工程；最终成果由项目状态、规则系统、审核流水线和组件版本共同决定。**

### 主体关系

本项目不是：

```
AI → HTML
```

而是：

```
Project → Workflow → Skills → Review → Publish
```

> **主体永远是 Project。** AI 是 Project 流程中的参与者，不是最终结果的产出方。

### 系统层级（V2）

```
Web
  ↓
Service  ← 文件操作、目录管理、版本管理、状态校验的唯一入口
  ↓
Skill    ← 只负责「输入 → 输出」，不触碰文件系统
  ↓
Service
  ↓
Project  ← 唯一数据主体
```

**Skill 不允许：** 改 JSON、建目录、写 review、建版本。

**Skill 只负责：** 输入 → 输出。

**所有文件操作交给 Service。**

> 这是整个系统以后稳定性的关键。

## 二、核心工作流程

```
创建品牌项目
    ↓
录入品牌资料
    ↓
AI 分析品牌语言
    ↓
用户确认品牌方向
    ↓
生成品牌资源
    ↓
生成整套组件初稿
    ↓
进入组件审核工作台
    ↓
逐个预览、修改、对比、确认
    ↓
形成企业品牌组件库
    ↓
导入已有公众号文章
    ↓
匹配并替换文章组件
    ↓
公众号兼容编译
    ↓
导出最终 HTML
```

第一版采用：**整套初稿生成 + 单组件审核修改**，而不是让 AI 每次只生成一个组件。

这样可以保证初始设计方向统一，同时允许用户逐个打磨。

## 三、项目分层

整个项目分为五层。

### 1. 架构层

负责定义项目中的核心对象和文件结构。

主要对象：

- `BrandProject`
- `BrandProfile`
- `BrandAnalysis`
- `BrandSystem`
- `BrandAsset`
- `BrandComponent`
- `ComponentVersion`
- `ReviewRecord`
- `ArticleTemplate`
- `PublishArtifact`

> 这一层不依赖具体 AI 模型。

### 2. 品牌逻辑层

负责定义 AI 的设计流程：

```
品牌资料 → 品牌分析 → 品牌系统 → 品牌资源 → 组件规划 → 整套组件初稿 → 单组件修改
```

这一层负责告诉 AI：

- 先分析什么
- 输出什么
- 如何使用品牌资源
- 如何参考已确认组件
- 修改组件时哪些内容不可改变

### 3. 规则与契约层

负责约束 AI、程序和公众号输出。包括四类规则：

| 规则类型    | 说明                                                     |
| ----------- | -------------------------------------------------------- |
| 程序规则    | 组件必须符合统一数据结构                                 |
| 品牌规则    | 规定 Logo、角标、纹样、图标等品牌资源如何使用            |
| 公众号规则  | 规定允许的 HTML、CSS 和资源形式                          |
| AI 输出规则 | AI 必须输出结构化组件数据，不能只返回一段不可管理的 HTML |

### 4. 实现层

负责开发实际程序，包括：

- 品牌项目管理
- 品牌分析
- 品牌资源管理
- 组件生成
- 组件预览
- 版本管理
- 审核管理
- 文章组件替换
- 公众号 HTML 编译

> TRAE Work、Codex 主要在这一层工作。

### 5. 审核层

负责用户查看和控制设计结果。包括：

- 实时预览
- 手机宽度预览
- 版本切换
- 修改意见
- 新旧版本对比
- 接受 / 拒绝 / 回退 / 锁定
- 公众号兼容报告

## 四、项目核心约束原则

> 所有 AI 之间的通信都**不要依赖自然语言对话**，而依赖**结构化文件**。

也就是说：

| 通信链路                               | 通信方式                                                      |
| -------------------------------------- | ------------------------------------------------------------- |
| 用户 ↔ Web                            | 通过界面交互                                                  |
| Web ↔ AI Agent（Trae Work、Codex 等） | 通过 Task 文件                                                |
| AI Agent ↔ 项目                       | 通过 BrandSystem、BrandAssets、Component、Review 等 JSON 文件 |
| 审核历史                               | 通过 Decision Log 持久化，而不是聊天记录                      |

> 这样整个系统就从"聊天驱动"升级为"**数据驱动**"，后续无论接入哪种 AI，都只需要遵守数据契约和任务协议即可。

## 五、第一版功能范围

第一版**不要一次做三十个组件**。先实现完整闭环，再扩充组件数量。

1. 开头封面 Cover
2. 一级标题 Heading 1

5. 重点提示 Notice
6. FAQ

这 8 个组件已经足以验证：

- 品牌资源是否能贯穿组件
- 不同组件是否保持统一
- AI 修改是否可控
- 文章应用是否能正常工作
- 公众号兼容编译是否有效

### 后续扩展组件

## 七、品牌系统结构

> **BrandSystem 是整个项目最核心的数据。所有 Skill 都必须读取它。**

`BrandSystem` 不是简单的「颜色 + 字体」，而是一套完整的品牌工程规范：

```
品牌原则 → 视觉语言 → 设计 Token → 品牌资源规范 → 组件规范
```

```json
{
```

### 组件版本

```json
{
  "version": 2,
  "createdAt": "2026-08-02T00:00:00Z",
  "createdBy": "ai",
  "instruction": "减少背景纹样，增加答案区域留白",
  "sourceHtml": "<section>...</section>",
  "publishHtml": "<section>...</section>",
  "assetRefs": ["brand-mark-primary"],
  "compatibility": {
    "status": "passed",
    "warnings": []
  }

```

> 每次 AI 修改都必须创建新版本，**不能直接覆盖旧版本**。

### Design Memory（设计记忆）

> **每个 BrandProject 都有一份 Design Memory。AI 修改任何组件前，第一步必须读取它。**

作用：让整个品牌的组件**越来越统一**，而不是每个组件越来越不像一家公司的。

`brand-projects/nova-tech/design-memory.json`：

```json
{
  "coverStyle": "hero-minimal",
  "faqStyle": "card-outline",
  "dividerStyle": "dot-gradient",
  "preferredPattern": "grid-light",
  "decisions": ["减少背景纹样", "品牌角标缩小", "保持大留白"]
}
```

**读取规则：**

- 整套组件生成：读取 Design Memory（若存在），保证方向一致
- 单组件修改：读取 Design Memory，保证新版本不偏离既定风格
- 组件确认：将关键风格决策写回 Design Memory

## 十、组件生成流程

> V2 起，组件生成由 **component-designer Skill** 统一负责。Skill 只做「输入 → 输出」，所有文件读写由 Service 完成。

### 整套组件初稿生成

**AI 输入：**

- BrandProfile
- BrandAnalysis
- BrandSystem
- BrandAssets
- DesignMemory
- ComponentList
- ProgramRules
- WechatRules

**AI 输出：**

- Cover
- Heading1
- Heading2
- Quote
- Notice
- FAQ
- CTA
- Footer

每个组件都必须输出：

- 组件数据
- 资源引用
- HTML 源码
- 设计说明
- 兼容性声明

### 单组件修改

**用户提出：**

> 保留当前 FAQ 的整体结构。
> 把问题编号改为品牌角标；
> 减少背景纹样；
> 答案上下留白增加；
> 不要修改品牌颜色和字体层级。

**系统发送给 AI：**

- 品牌系统
- 品牌资源
- DesignMemory
- 当前 FAQ 版本
- Review Record（review.json）
- 用户修改意见
- 已确认组件摘要
- 程序规则
- 公众号规则

AI 只返回 FAQ 新版本。

**不得修改：**

- BrandSystem
- 已确认的其他组件
- 非当前组件资源
- 用户没有要求修改的内容

## 十一、审核工作台

页面建议采用三栏结构。

```
┌──────────────┬────────────────────────┬────────────────────┐
│  组件列表    │       组件预览         │     审核面板       │
│              │                        │                    │
│ 封面  已确认 │ 手机宽度实时预览       │ 当前版本 v3        │
│ H1    已确认 │                        │ 设计说明           │
│ H2    待审核 │                        │ 使用资源           │
│ FAQ   修改中 │                        │ 兼容检查           │
│ CTA   未审核 │                        │ 修改意见输入框     │
└──────────────┴────────────────────────┴────────────────────┘
```

### 审核操作

- 接受当前版本
- 提出修改
- 重新设计
- 与上一版本对比
- 回退到上一版本
- 设为最终版本
- 锁定组件

### 审核状态

```
not-generated
draft
reviewing
revision-requested
approved
locked
failed
```

### 修改对比

至少展示：

- HTML 视觉对比
- 修改说明
- 资源变化
- 样式参数变化
- 兼容性变化

例如：

| 项目           | 原值 | 新值             |
| -------------- | ---- | ---------------- |
| Logo 尺寸      | 32px | 24px             |
| Pattern 透明度 | 12%  | 6%               |
| 内容内边距     | 24px | 30px             |
| 资源移除       | —    | pattern-dot-grid |

## 十二、程序规则

组件生成必须满足以下规则。

### HTML 规则

第一版**允许**：

```
section div p span strong em blockquote img br
```

后续可以根据真实测试扩展。

**禁止**：

```
script iframe form input video audio canvas object embed
```

### CSS 规则

第一版要求：

- 使用内联样式
- 不依赖外部 CSS
- 不使用 JavaScript
- 不使用 CSS 变量作为最终发布格式
- 不使用外部字体

> 内部预览可以使用 class 和 CSS 文件。发布时必须编译为内联样式。

### 资源规则

- 所有资源必须登记 `assetId`
- 禁止引用未知外部资源
- SVG 必须存在降级方案
- 图片必须有宽度约束
- 装饰元素不能遮挡正文
- Base64 资源必须限制体积

### 内容规则

- 正文必须可编辑
- 标题、问题、答案等字段必须能被程序识别
- 不得将业务内容画进 SVG
- 不得将长文本写入背景图片
- 组件必须支持长文本和短文本

## 十三、公众号编译器

公众号编译器必须是**确定性代码**，不应主要依赖 AI。

### 主要流程

```
组件源码
  ↓
结构校验
  ↓
标签白名单过滤
  ↓
CSS 白名单过滤
  ↓
样式内联
  ↓
资源处理
  ↓
SVG 降级
  ↓
HTML 清理
  ↓
兼容性检查
  ↓
输出发布 HTML
```

### 编译输出

每个组件保留两个版本：

- `sourceHtml`：用于系统内部预览和编辑
- `publishHtml`：用于公众号发布

### 兼容报告

```json
{
  "status": "passed-with-warnings",
  "changes": ["SVG纹样已转换为PNG", "外部样式已全部内联"],
  "warnings": ["阴影效果在部分客户端可能略有差异"],
  "errors": []
}
```

> 存在错误时，组件不能进入 `approved` 状态。

## 十四、文章应用流程

用户导入一篇已有文章。

系统先解析文章中的结构：

- 文章标题
- 开头封面
- 一级标题
- 二级标题
- 引用
- 提示
- FAQ
- CTA
- 结尾
- 普通正文
- 图片

然后根据组件类型进行映射：

| 原文章结构 | 品牌组件      |
| ---------- | ------------- |
| 原封面     | 品牌 Cover    |
| 原一级标题 | 品牌 Heading1 |
| 原引用     | 品牌 Quote    |
| 原 FAQ     | 品牌 FAQ      |
| 原结尾     | 品牌 Footer   |

> 普通正文不要强行组件化，只应用：正文字体、字号、行高、段间距、链接样式、图片样式。

### 最终流程

```
文章 AST
  ↓
组件类型匹配
  ↓
填充品牌组件内容
  ↓
组合完整文章
  ↓
公众号编译
  ↓
最终 HTML
```

### Service 层职责

> Service 是 Skill 与 Project 之间唯一的桥梁。

```
Web → Service → Skill → Service → Project
```

Service 负责：

- 读写 JSON 文件
- 创建目录
- 管理组件版本
- 校验 Schema
- 写入 review / decision-log
- 管理任务队列（inbox / processing / done / failed）
- 状态流转（draft → reviewing → approved → locked）

**Skill 不得绕过 Service 直接操作文件系统。**

### 阶段一：Project + Schema + Service

**目标：** 建立项目、品牌、资源、组件和版本的数据结构，以及 Service 层。

**需要完成：**

- BrandProject 类型
- BrandProfile 类型
- BrandSystem 类型
- BrandAsset 类型
- BrandComponent 类型
- ComponentVersion 类型
- ReviewRecord 类型
- DesignMemory 类型
- JSON Schema 校验
- **Service 层**（文件/目录/版本/状态的唯一入口）
- 本地项目读写（必须经 Service）

**验收标准：**

- 可以创建一个品牌项目
- 可以保存品牌资料
- 可以保存资源
- 可以保存组件和多个版本
- 数据不符合 Schema 时无法保存
- **所有文件操作必须经 Service，不允许直接写文件**

### 阶段二：Review Pipeline（审核流水线）

#### 设计目标

第二阶段**不负责设计组件**，而是建立整个品牌组件审核系统。

该系统采用 **Human in the Loop** 模式：

- **AI 负责生成，用户负责审核，系统负责记录，Agent 负责修改。**
- 所有审核结果必须**结构化保存**，而不是依赖聊天记录。

整个流程如下：

```
Brand Components
    │
    ▼
Pending（待审核）
    │
    ▼
Review Workspace（Web）
    │
    ┌──────┴────────┐
    │                │
   通过             驳回
    │                │
    ▼                ▼
Approved       Revision Task
                    │
                    ▼
                Workspace Inbox
                    │
                    ▼
                Trae Work Agent
                    │
                    ▼
                新版本组件
                    │
                    ▼
                Pending（重新进入循环）
```

形成完整闭环。

#### Review Workspace（Web）

第二阶段必须开发一个独立的 Web 审核工作台。

> 工作台**不负责生成组件**。

只负责：

##### ① 浏览组件

例如：

```
品牌组件
- Cover
- Heading1
- Heading2
- Quote
- FAQ
- CTA
- Footer
```

点击任意组件，显示：

- 组件名称
- 当前版本
- 手机预览
- 公众号预览
- 设计说明
- 使用品牌资源
- 兼容性结果

##### ② 审核组件

审核项：

- 品牌一致性
- 视觉效果
- 信息层级
- 公众号兼容性
- 资源使用
- 整体满意度

用户可以：

- 通过
- 驳回
- 评分
- 填写修改意见

##### ③ 自动生成修改任务

当用户点击「重新设计」，系统自动生成标准化 Task。

例如：

```json
{
  "taskId": "task-000031",
  "projectId": "nova-tech",
  "component": "faq",
  "currentVersion": 3,
  "action": "redesign",
  "instruction": "减少背景纹样50%，品牌角标缩小，增加答案留白",
  "priority": "normal",
  "createdAt": "2026-08-02T12:00:00Z"
}
```

> Task **不直接发送给 AI**，而是进入任务队列。

#### Workspace Queue

整个工作区新增统一任务目录。

```
workspace/
├── inbox/
├── processing/
├── done/
├── failed/
└── logs/
```

各目录职责：

| 目录          | 职责            |
| ------------- | --------------- |
| `inbox/`      | 等待 Agent 处理 |
| `processing/` | Agent 正在处理  |
| `done/`       | 已经完成        |
| `failed/`     | 执行失败        |
| `logs/`       | 保存执行日志    |

> Agent **不扫描整个项目**，只监听 `workspace/inbox/`。
>
> 这样后续替换 Trae、Codex、Claude Code 时无需修改项目结构。

#### Trae Work Agent 工作流程

Trae Work 不需要聊天，只需要执行：

```
发现 inbox 中的新任务
    ↓
读取 Task
    ↓
读取 BrandSystem
    ↓
读取 BrandAssets
    ↓
读取当前组件
    ↓
读取 Review
    ↓
生成新版本
    ↓
保存组件
    ↓
移动 Task 到 done
```

如果失败：移入 `failed/`，并生成错误日志。

#### Review Record

每个组件新增审核记录。

例如：`faq/review.json`

```json
{
  "status": "revision",
  "score": 72,
  "reviewer": "human",
  "comments": ["品牌识别度不足", "角标太大", "答案区域留白太少"]
}
```

> AI 修改时读取 `review.json`，**而不是聊天记录**。

#### Decision Log

新增设计决策日志。

例如：

```json
[
  {
    "version": 1,
    "decision": "reject",
    "reason": "品牌感不足"
  },
  {
    "version": 2,
    "decision": "reject",
    "reason": "FAQ层级不明显"
  },
  {
    "version": 3,
    "decision": "approve"
  }
]
```

作用：记录整个组件的设计演进。

方便：

- AI 学习历史决策
- 用户查看修改过程
- 回滚历史版本

#### 新增目录结构

在项目目录中增加：

```
workspace/
├── inbox/
├── processing/
├── done/
├── failed/
└── logs/
```

每个组件增加：

```
components/
└── faq/
    ├── component.json
    ├── review.json
    ├── decision-log.json
    ├── versions/
    └── approved.json
```

#### 阶段二验收标准（更新）

完成后必须支持：

- 创建 Review Task
- Web 查看所有待审核组件
- Web 手机预览
- Web 公众号预览
- 填写修改意见
- 自动生成 Task
- Task 自动进入 Inbox
- Trae Work 可读取 Task
- 新版本重新进入 Pending
- Review、Decision Log 自动更新
- Approved 版本不可直接覆盖
- **全流程无需依赖聊天记录**

### 阶段三：Brand Designer Skill

> 对应 V2 Skill 架构中的 `brand-designer`。第一版接入一个 AI 模型即可。

**需要完成：**

- 品牌资料 → BrandAnalysis
- BrandAnalysis → BrandSystem
- BrandSystem → 品牌资源

**第一版资源：** Logo、Brand Mark、Pattern、Divider

**Skill 约束：**

- Skill 只接收结构化输入，返回结构化输出
- 文件写入由 Service 完成
- 必须读取并遵守 BrandSystem 规范（生成资源时）

**验收标准：**

- AI 输出符合 Schema
- 资源能在工作台预览
- 用户可以确认品牌方向
- 用户可以重新生成单个资源
- Skill 不直接写文件

### 阶段四：Component Designer Skill

> 对应 V2 Skill 架构中的 `component-designer`，整合原"整套组件生成 + 单组件修改"两个阶段。

#### 4.1 整套组件初稿生成

根据已确认 BrandSystem 和 BrandAssets，生成 8 个组件。

**验收标准：**

- 8 个组件一次生成
- 每个组件都有独立版本
- 每个组件使用统一品牌资源
- 组件都通过程序结构校验
- 未通过兼容检查的组件显示错误

#### 4.2 单组件 AI 修改

**需要完成：**

```
用户修改意见
  ↓
读取当前组件
  ↓
读取品牌系统
  ↓
读取品牌资源
  ↓
读取 DesignMemory
  ↓
读取 Review Record
  ↓
生成新版本
  ↓
自动显示对比
```

**验收标准：**

- 只修改目标组件
- 其他组件和品牌资源不被改变
- 新版本保留旧版本
- 能接受或拒绝新版本
- 能回滚
- 修改结果必须符合 DesignMemory 的既定风格

### 阶段五：Article Apply（文章套用）

第一版支持导入结构化 HTML 或内部文章格式。

**需要完成：**

- 识别标题、引用、FAQ 等结构
- 替换为品牌组件
- 填充原文章内容
- 保留普通正文
- 编译为公众号 HTML

**验收标准：**

- 一篇已有文章可以自动套用品牌组件
- 原文章内容不丢失
- 组件结构正确
- 最终 HTML 可导出

### 阶段六：Compiler（公众号编译器）

> 公众号编译器是**确定性代码**，不依赖 AI。

**需要完成：**

- HTML 解析
- 标签白名单
- CSS 白名单
- 样式内联
- 资源引用校验
- SVG 转 PNG 接口
- 公众号发布 HTML
- 兼容报告

**验收标准：**

- 非法标签被拦截
- 未登记资源无法发布
- SVG 有降级结果
- 能生成 sourceHtml 和 publishHtml
- 存在错误时无法确认组件

## 十八、推荐第一阶段技术栈

根据现有项目技术栈决定，不需要为了这个功能全部重写。

如果当前是 React/TypeScript，建议：

| 类别      | 选型                        |
| --------- | --------------------------- |
| 前端      | React + TypeScript + Vite   |
| 状态管理  | Zustand 或现有状态管理      |
| 后端      | Node.js + TypeScript        |
| 数据      | 第一版使用本地文件或 SQLite |
| HTML 处理 | parse5 / posthtml / cheerio |
| CSS 处理  | postcss / juice             |
| Schema    | zod / ajv                   |
| 预览      | iframe + srcDoc             |
| 版本      | 文件版本或数据库版本表      |

> 不要第一版就引入复杂微服务。

## 十九、第一版暂不实现

以下能力不进入当前版本：

- 多模型自动路由
- 插件市场
- 第三方设计 Agent 协议
- 多人实时协作
- 云端素材市场
- 自动发布公众号
- 复杂 AI 评分系统
- 完整 Figma 式设计编辑器
- 自动生成三十种组件变体

这些会拖慢核心闭环。

**当前只做：** 品牌分析、资源生成、整套组件生成、单组件审核修改、文章套用、公众号导出。
