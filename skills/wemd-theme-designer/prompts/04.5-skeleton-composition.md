# Stage 4.5: Skeleton Composition（翻译阶段 · 形）

> 位于 Stage 4（Component Analysis）与 Stage 5（Component Mapping）之间。
> 本阶段只设计组件的**形**（骨架构图），**不写 HTML / CSS / 任何 CSS 值**。
> DSL 规范见 `reference/skeleton-design-spec.md`（v3 · DSL 定稿）。

## 本阶段任务

为选定组件设计**构图骨架**：用一棵空间树描述组件视觉上怎么构图、结构怎么组织。

骨架 = 一棵嵌套的空间树，`group` 是核心结构单元：

```text
根容器 (layout)
 ├── 区域 A
 ├── 区域 B (layout)
 │    ├── 区域 B1
 │    └── 区域 B2
 └── 区域 C
```

## 输入

1. `themes/{theme-name}/states/component_strategy.json`（上一阶段三分类结果，含 Brand Anchor 的 score）
2. `themes/{theme-name}/states/visual_language.json`（视觉语言，决定构图气质）
3. `themes/{theme-name}/states/concept_state.json`（视觉母题，决定构图来源）
4. `registry/components.json`（组件注册表，确认组件能力与品牌表达力）
5. `reference/skeleton-design-spec.md`（v3 DSL 规范 + §10 Slot 契约速查；abbr 由主程序 `slotDefs.ts` 唯一决定）

## 前置认知：layout 与 group 的职责划分（关键）

- **`layout`** 是**容器级**概念：描述"父容器内部如何组织孩子"。
  - 枚举：`stack` / `centered` / `side-rail` / `split` / `grid` / `media-text`。
  - 只回答"这群孩子怎么排"，不描述具体 region 内部。
- **`group`** 是**区域边界**：描述"哪里是一个视觉区域"。
  - 有 `name`（语义边界名）+ 可选 `layout` + `regions`（递归）。
  - 二者正交：一个 group 既有边界，又有自己组织孩子的方式。

```text
group(main)
    layout: side-rail
    ├── decoration  quote-mark (relation: overlay)
    └── slot        quote
```

## 该为哪些组件设计骨架？（决策标准）

不是"能写就写"，而是"有刻意构图理由才写"。**无理由不产出。**

| 条件                                            | 做法                               |
| ----------------------------------------------- | ---------------------------------- |
| Brand Anchor（score ≥ 7）                       | **必须**设计骨架。这是"放飞"的体现 |
| Content/Utility，但视觉母题使其**需要特殊构图** | **可以**设计骨架                   |
| Content/Utility，默认骨架已够用                 | **不写**，留空回退默认骨架         |

## 铁律（违反即非法骨架）

1. **只描述视觉空间如何组织**，不描述 DOM/CSS 怎么实现。
2. **禁止任何 CSS 值**：`padding` / `margin` / `font-size` / `color` / `width` / `height` / `border` / `flex` / `grid-template-columns` / `gap` / `align-items` 等一律不得出现。
3. **Slot 固定**：`slot` 字段必须引用该组件已注册的 slot key，禁止自创。
4. **group 嵌套 ≤ 2 层**。
5. **不写 class 名**：class 由 Compiler 确定性推导，AI 不参与命名。

## 设计步骤

1. **读母题**：从 `concept_state.json` 的 `visual_objects` / `material_language` 判断骨架构图来源。
2. **定 Anchor 名单**：至少为 Brand Anchor（score≥7）设计骨架。
3. **逐组件构图**：对每个决定设计的组件，用空间树描述构图；有特殊构图理由的 Content/Utility 也纳入。
4. **校验**：对照 `skeleton-design-spec.md` 的 layout 枚举、region 类型、decoration/label 预定义集、Slot 契约。

## 输出格式

严格遵循 `schema/skeleton_intent.schema.json`：

```json
{
  "schema": "SkeletonIntent",
  "note": "允许任意组件提供骨架；未提供/非法则回退全局默认骨架",
  "skeletons": {
    "quote-card": {
      "component": "quote-card",
      "layout": "stack",
      "regions": [
        {
          "type": "group",
          "name": "header",
          "layout": "stack",
          "regions": [
            { "type": "label", "name": "quote-label", "text": "QUOTE" }
          ]
        },
        {
          "type": "group",
          "name": "main",
          "layout": "side-rail",
          "regions": [
            {
              "type": "decoration",
              "name": "quote-mark",
              "relation": "overlay"
            },
            { "type": "slot", "slot": "quote" }
          ]
        },
        { "type": "slot", "slot": "author" }
      ]
    }
  }
}
```

## 规则

1. 只收录有刻意构图理由的组件；无理由不产出。
2. 每个骨架必须引用**已注册**的 slot key（契约固定）。
3. decoration / label 的 `name` 只能引用 `skeleton-design-spec.md` §5 预定义集。
4. 出现任何 CSS 值，视为非法骨架。
5. 本阶段**不决定颜色/字体/间距**——那是 Stage 5（Component Mapping / 皮）的职责。
